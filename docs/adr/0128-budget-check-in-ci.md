# ADR 0128: CI で予算違反を見つけ、予算ごとに一つの issue にまとめる

Status: superseded [{"part":"実装すること (スクリプト bin/budget-check)","by":["docs/adr/0132-budget-check-separate-measure-and-report.md"],"kind":"supplement"},{"part":"実装すること (そのほか: CI のジョブの例)","by":["docs/adr/0132-budget-check-separate-measure-and-report.md"],"kind":"replace"}]

## 文脈

本人から、CI で予算違反を見つけたときに issue を自動で立てるよう頼まれた。
同じ内容の issue があるときは、issue を増やさず、有用な観点だけをコメントに残す。
本人は、使い回せるスクリプトを作ること (各リポジトリの CI から呼ぶ) と、コメントを残すかを機械的に決めることを選んだ。

予算は、ADR の受けいれ条件と、リポジトリの予算の一覧 (`docs/budgets.md`) に書く ([ADR 0126](0126-audit-skill.md)、提案)。
[ADR 0126](0126-audit-skill.md) の `conformance-audit` は、頼まれたときに `auditor` が予算違反を探す。この ADR は、それとは別に、CI が毎回、機械的に予算を確かめる。

共通のハーネスの設定は dotfiles に置き、配ることは今は考えない (本人の決定)。そのため、スクリプトも dotfiles に置く。
この ADR の実装は、[ADR 0124](0124-invariant-and-test-naming.md) (テストの名前) と [ADR 0126](0126-audit-skill.md) (予算の一覧の形) の採択と実装の後に行う。

## 調査した事項

- dotfiles (`tett23/dotfiles`) と Golem (`tett23/golem`) は、どちらも公開のリポジトリである (`gh repo view --json visibility` が `PUBLIC` を返した)。
  そのため、Golem の CI は、`actions/checkout` で dotfiles を、決めたコミットに固定して取得できる。
- dotfiles の CI (`.github/workflows/ci.yml`) は、`zsh/tests/*.test.zsh` をすべて動かす `zsh-tests` のジョブと、`bin/` のスクリプトを並べて検査する shellcheck のジョブ (29 行が `shellcheck` の行で、対象のファイルの一覧は 30〜33 行) を持つ。
- [ADR 0126](0126-audit-skill.md) は、予算の一覧の各行に、名前、指標と単位、比較 (`<=` か `>=`)、値、計測のコマンド、決めた ADR と番号を書くとする。計測のコマンドは、リポジトリのルートで動かすと、計測した値を一つの数として標準出力の最後の行に出す。
- `gh issue list` は、件数を `--limit` で決め、既定は 30 件である (`gh issue list --help` の「default 30」)。`gh api` は `--paginate` を付けないと、一つのページの分しか返さない。
- 存在しないラベルで `gh issue list -R tett23/dotfiles --label nonexistent-label-xyz --state open --json number` を呼ぶと、空の一覧 `[]` を返し、失敗しない。
- `gh api --paginate` は、ページごとに別の JSON の配列を出す (`gh api --help` の「Each page is a separate JSON array」)。一つの配列にまとめるには `--slurp` か `jq -s` が要る。
- 存在しないラベルを付けて `gh issue create` を呼んだときに失敗するかは、確かめていない。`gh label create` に `issues: write` の権限で足りるかも、確かめていない。そのため、issue を作る前に `gh label create <ラベル> --force` (あれば上書き) でラベルを用意する。

- 起票の条件として、次の 3 つの形を比べた (本人との検討)。
  - A. 一回の CI で、計測を一回する。違反した最初の実行で見つかるが、計測のぶれで違反になることがある。
  - B. 計測のコマンドが、同じ実行の中で何回か測り、中央値か 95 パーセンタイルを出す。見つかるのは違反した最初の実行で、遅れない。同じ機械の中のぶれは抑えるが、CI の機械が変わることによるぶれは抑えない。CI の時間は回数の分だけ延びる。
  - C. 複数の CI の実行にまたがり、直近の何回かの値の中央値か 95 パーセンタイルで決める。中央値は、直近 K 回のうち過半数が違反するまで見つからない (K が 5 なら 3 回目)。95 パーセンタイルは、K が小さいとほぼ最大値になり、ぶれを抑えない。違反していない回の値も残す場所 (Actions のキャッシュ、別の issue など) が要り、設計が大きく増える。
  本人は B を選んだ。C は、調べたうえでやめた。

## 実装すること

### スクリプト `bin/budget-check`

POSIX の `sh` と `awk`、`gh`、`jq` で書く。使いかたは `bin/budget-check [--dry-run] [--fail-on-violation] [予算の一覧のパス]` で、パスを省いたときは `docs/budgets.md` とする。

予算の一覧を読む:

1. リポジトリのルートは `git rev-parse --show-toplevel` で決め、計測のコマンドはルートで動かす。予算の一覧のパスは、リポジトリのルートから見た相対パスに直して使う (`./docs/budgets.md` も絶対パスも `docs/budgets.md` になる)。git のリポジトリの外で動かしたときと、パスがリポジトリの外を指すときは、エラーとして終了コード 1 で終わる。
2. パスを省き、`docs/budgets.md` が無いときは、「予算なし」と標準出力に出して、終了コード 0 で終わる。パスを引数で渡し、そのファイルが無いときは、エラーとして終了コード 1 で終わる (打ち間違いを見逃さないため)。
3. ファイルの中で、見出しの行が `| 名前 | 指標と単位 | 比較 | 値 | 計測のコマンド | ADR |` の表を探す。この表が無いときは、エラーを標準エラーに出して終了コード 1 で終わる。表に行が無いときは、何もせず終了コード 0 で終わる。
4. 各行のセルの前後の空白を除き、インラインのコードの印 (`` ` ``) を外し、`\|` を `|` に戻す。セルの数が 6 でない行と、名前がそれより前のどれかの行と同じ行は、その行の予算をエラーとする (名前が同じ二つ目以降の行)。

予算ごとに確かめる (一つの予算のエラーは記録して、ほかの予算を続ける):

5. 比較が `<=` でも `>=` でもないとき、値が数でないときは、その予算をエラーとする。数は、正規表現 `^-?[0-9]+(\.[0-9]+)?$` に合う文字列とする。
6. 計測のコマンドを `sh -c` で動かし、標準出力の最後の空でない行を計測の値とする。コマンドが 0 でない終了コードで終わったとき、または計測の値が数でないときは、その予算をエラーとする。
7. 比較が `<=` なら「計測の値 <= 値」、`>=` なら「計測の値 >= 値」のときに予算を満たすとし、満たさないときを違反とする。
8. その予算の issue の題を `予算違反: <名前> (<リポジトリのルートから見た予算の一覧の相対パス>)` とする。モノレポで予算の一覧が二つあっても、題がぶつからない。

issue とコメント:

9. `gh issue list --label budget-violation --state open --limit 1000 --json number,title,body` で開いた issue を読み、題が一字も違わないものを探す。二つ以上あるときは、番号の小さい一つを使う。
10. 使う issue があるときは、`gh api --paginate --slurp repos/{owner}/{repo}/issues/<番号>/comments` でコメントをすべて読む。本文とコメントを古い順に並べ、正しい印を持つもののうち、いちばん新しいものを前の記録とする。正しい印は、`<!-- budget-check: value=<数> state=<violation|ok> -->` の形で、`<数>` が上の正規表現に合い、`state` が `violation` か `ok` のものである。正しくない印は読み飛ばす。正しい印が一つも無いときは、前の記録が無いものとする。
11. 次の表で、することを決める。「悪い」は、比較が `<=` なら計測の値が前の値より大きいこと、`>=` なら小さいことである。

    | 今の結果 | 開いた issue | 前の記録 | すること |
    | --- | --- | --- | --- |
    | 違反 | 無い | (なし) | ラベルを用意し、issue を作る |
    | 違反 | ある | 無い | 違反のコメントを足す |
    | 違反 | ある | `state=ok` | 違反のコメントを足す (また違反した) |
    | 違反 | ある | `state=violation` で、今の値のほうが悪い | 違反のコメントを足す |
    | 違反 | ある | `state=violation` で、今の値が同じかよい | 何もしない |
    | 満たす | ある | `state=violation` | 「予算を満たした」コメントを足す |
    | 満たす | ある | `state=ok` か無い | 何もしない |
    | 満たす | 無い | (なし) | 何もしない |

12. issue の本文には、予算の行、計測の値、コミット (`$GITHUB_SHA`)、CI の実行への URL (`$GITHUB_SERVER_URL/$GITHUB_REPOSITORY/actions/runs/$GITHUB_RUN_ID`)、決めた ADR を書く。違反のコメントには、計測の値、前の記録があれば前の値との差、コミット、URL を書く。「予算を満たした」コメントには、計測の値、コミット、URL を書く。本文とコメントの末尾に、その時点の印を置く。issue は閉じない (閉じるのは本人)。
13. `gh` が 0 でない終了コードで終わったとき (権限、ネットワークなど) は、その予算をエラーとする。

終わり方:

14. `--dry-run` のときは、`gh label create`、`gh issue create`、`gh issue comment` を呼ばず、するはずのことを標準出力に出す。読むための `gh issue list` と `gh api` は呼ぶ。
15. 終了コードは、予算の一覧が読めないとき (引数のファイルが無い、決まった見出しの表が無い、git のリポジトリの外、パスがリポジトリの外) か、エラーの予算が一つでもあれば 1 とする。エラーが無く、違反の予算があり、`--fail-on-violation` を付けたときは 2 とする。それ以外は 0 とする。

### テスト

`zsh/tests/budget-check.test.zsh` を足す。`gh` は、`PATH` の先頭に置いた偽の `gh` で置き換え、issue とコメントとラベルの状態をファイルに記録する。偽の `gh` は、決めた引数で失敗させることもできるようにする。テストの名前は、下の不変条件の番号を先頭に持つ (`check "ADR 0128 I1: …"`)。

### そのほか

- `.github/workflows/ci.yml` の shellcheck のジョブの一覧に、`bin/budget-check` を足す。
- `agents/skills/conformance-audit/SKILL.md` の予算の一覧の書き方に、「ぶれる指標の計測のコマンドは、同じ実行の中で何回か測り、その中央値か 95 パーセンタイルを出す」を足す (上の B)。
- `agents/skills/conformance-audit/SKILL.md` に、CI で予算を確かめるときは `bin/budget-check` を使うことと、各リポジトリの CI に足すジョブの例を書く。例は、`actions/checkout` で `tett23/dotfiles` をコミットに固定して取得し、`gh` に `GITHUB_TOKEN` (`issues: write` の権限) を渡して `bin/budget-check` を動かし、同じ予算の実行が重ならないように `concurrency` を付ける形とする。
- `docs/specifications.md` に、`bin/budget-check` と、その使いかたを書く。README は変えない。
- 各リポジトリの CI にジョブを足すこと、どのイベントで動かすかは、そのリポジトリの ADR で決める。

## 実装しないこと

- 複数の CI の実行にまたがる集計 (中央値や 95 パーセンタイル) で起票を決めること (上の C)。調べたうえでやめた。検出が遅れ、値を残す場所の設計が要るためである。計測のぶれが課題になったら、`docs/benchmarks/` の記録や issue のコメントに残る値を見て、別の ADR で検討する。
- 違反が止んだときに issue を自動で閉じること。
- コメントを残すかを、モデルに判定させること。
- 予算の一覧と ADR の受けいれ条件の食い違いを、このスクリプトで見つけること。`conformance-audit` で扱う。
- dotfiles の CI に、予算を確かめるジョブを足すこと。dotfiles には予算が無い。スクリプトのテストは、今の `zsh-tests` のジョブで動く。

## 不変条件

以下の「書き込みが成功した実行」は、`--dry-run` を付けず、その予算の `gh` の呼び出しがすべて 0 で終わった実行を指す。

- I1: 書き込みが成功した実行の後、違反の予算には、その題とラベル `budget-violation` を持つ開いた issue が一つ以上あり、スクリプトがコメントを足すのは、そのうち番号の小さい一つだけである。
- I2: ラベル `budget-violation` の開いた issue が 1000 件以下のとき、違反の予算に、その題とラベルの開いた issue がすでにあれば、スクリプトは issue を作らない。
- I3: 違反の予算に開いた issue があるとき、コメントが増えるのは、前の記録が無いとき、前の記録が `state=ok` のとき、前の記録が `state=violation` で今の値のほうが悪いときだけで、増えるコメントは一つである。
- I4: 予算を満たすとき、issue は作られない。開いた issue があり、前の記録が `state=violation` のときだけ、「予算を満たした」コメントが一つ増える。
- I5: 計測の値が値に等しいときは、比較が `<=` でも `>=` でも、予算を満たす。
- I6: エラーの予算 (セルの数が 6 でない、名前がそれより前のどれかの行と同じ、比較か値か計測の値が決まりに合わない、計測のコマンドが失敗した、`gh` が失敗した) について、スクリプトは issue を作らずコメントも足さない。ほかの予算の確かめは続ける。
- I7: `--dry-run` のとき、`gh label create`、`gh issue create`、`gh issue comment` は一度も呼ばれない。
- I8: 終了コードは、予算の一覧が読めないかエラーの予算があれば 1、エラーが無く違反があり `--fail-on-violation` があれば 2、それ以外は 0 である。
- I9: パスを省いて `docs/budgets.md` が無いとき、または表に行が無いとき、`gh` は一度も呼ばれず、終了コードは 0 である。
- I10: 前の記録は、本文とコメントのうち正しい印を持ついちばん新しいものから読み、印の無いものと正しくない印は読み飛ばす。
- I11: 計測のコマンドとして動かす文字列は、セルの前後の空白とインラインのコードの印を外し、`\|` を `|` に戻したものである。
- I12: issue の題は `予算違反: <名前> (<リポジトリのルートから見た予算の一覧の相対パス>)` で、同じ予算と同じ一覧からは、引数の書き方によらず同じ題になる。

境界の入力:

| 入力 | 期待 | 不変条件 |
| --- | --- | --- |
| パスを省き、`docs/budgets.md` が無い | 「予算なし」と出し、終了コード 0 | I9 |
| 引数で渡したパスのファイルが無い | 終了コード 1 | I8 |
| 表はあるが行が無い | 何もせず終了コード 0 | I9 |
| ファイルはあるが、決まった見出しの表が無い | 終了コード 1 | I8 |
| `<=` 100 に対して計測が 100 | 満たす。issue を作らない | I5, I4 |
| `<=` 100 に対して計測が 100.0001 | 違反。issue を一つ作る | I1, I2 |
| `>=` 30 に対して計測が 30 | 満たす | I5 |
| 違反のまま 2 回目、計測が前と同じ | issue もコメントも増えない | I2, I3 |
| 違反のまま 2 回目、計測が前より悪い | コメントが一つ増える | I3 |
| 違反のまま 2 回目、計測が前よりよい (まだ違反) | コメントは増えない | I3 |
| 違反の issue があり、計測が予算を満たした | 「予算を満たした」コメントが一つ増え、issue は開いたまま | I4 |
| 満たした後の 2 回目も満たす | コメントは増えない | I4 |
| 満たした後 (前の記録が `state=ok`) にまた違反 | 違反のコメントが一つ増える | I3 |
| 同じ題とラベルの開いた issue が二つある | 番号の小さいほうにだけコメントする。issue を作らない | I1, I2 |
| 同じ題の issue が閉じたものだけある | issue を一つ作る | I1 |
| 同じ題でラベルの無い開いた issue がある | それは使わず、ラベル付きの issue を一つ作る | I1 |
| 開いた issue の本文とコメントに印が無い (または壊れている) | 前の記録が無いものとして、違反のコメントを一つ足す | I3, I10 |
| 二つの予算の一方が違反、もう一方が満たす | 違反の予算だけに issue を作る | I1, I4 |
| 一つの予算の計測のコマンドが終了コード 1、もう一つは違反 | 失敗の予算には何もせず、違反の予算には issue を作り、終了コード 1 | I6, I8 |
| 計測の値が `abc`、空、最後の行が空だけ | その予算はエラー | I6 |
| 比較が `<` | その予算はエラー | I6 |
| 値の列が `1e3` | その予算はエラー | I6 |
| 計測のコマンドに `\|` を含む (`seq 1 3 \| wc -l`) | `|` に戻して動かす | I11 |
| セルが 5 つの行 | その予算はエラー | I6 |
| 名前が同じ二つの行 | 二つ目の行の予算はエラー。一つ目は確かめる | I6 |
| `./docs/budgets.md` を引数で渡す | 題のパスは `docs/budgets.md` | I12 |
| 名前が 1 行目と 3 行目で同じ | 3 行目の予算はエラー | I6 |
| git のリポジトリの外で動かす | 終了コード 1 | I8 |
| いちばん新しい印が壊れていて、古い印が正しい | 古い正しい印を前の記録として読む | I10 |
| `gh issue create` が失敗 | その予算はエラー、終了コード 1 | I6, I8 |
| `--dry-run` で違反 | 書き込みの `gh` が呼ばれない | I7 |
| 違反があり `--fail-on-violation`、エラーなし | 終了コード 2 | I8 |
| 開いた issue が 31 件以上ある | 31 件目以降の issue も題で見つかる | I2 |
| ラベルの付いた開いた issue がちょうど 1000 件 | 1000 件目の issue も題で見つかる | I2 |
| ラベルの付いた開いた issue が 1001 件 | 1001 件目は読まれず、issue が重なりうる (I2 の前提の外。トレードオフ) | I2 |
| コメントが 31 件以上ある | 最後のページの印を前の記録として読む | I10 |

## 受けいれ条件

- A1: `zsh/tests/budget-check.test.zsh` の、上の不変条件の番号を持つテストがすべて通る。dotfiles の CI の `zsh-tests` と shellcheck のジョブも通る。
- A2: `conformance-audit` のスキルに、`bin/budget-check` の使いかたと、CI のジョブの例がある。

## テスト設計

- A1: 境界の入力の表の行を、それぞれテストにする。テストを先に書いて失敗させてから、スクリプトを書く。
  - 偽の `gh` は、`issue list` と `api` に記録のファイルの中身を JSON で返し、`label create`、`issue create`、`issue comment` を記録のファイルに足す。`issue list` の `--limit` と、`api` の `--paginate` が渡されたかも記録し、31 件以上の行のテストで確かめる。
  - 計測のコマンドは、テストのために `printf` で決まった値を出すコマンドにする。
- A2: 実装の後に、スキルを読み、`close-reading` で精読する。

## トレードオフ

- 前の値を issue の本文とコメントの印から読むので、人がその印を消したり変えたりすると、前の記録が無いものとして扱い、違反ならコメントを一つ足す。
- 計測のコマンドの値は、CI の機械によってぶれる。ぶれで悪くなったときも、コメントが増える。ぶれを避けるには、予算の値に余裕を持たせるか、計測のコマンドで何回かの中央値を出す。
- 開いた issue の読み込みを 1000 件で打ち切るので、ラベル `budget-violation` の開いた issue が 1000 件を超えると、issue が重なることがある。
- 各リポジトリの CI が dotfiles のコミットに固定して取得するので、スクリプトを直したときは、各リポジトリの固定を上げる。
