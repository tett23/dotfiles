# ADR 0063: usage-hint の表示を、画面に表示中のセッションで 1 分ごとに更新する

ステータス: 採択

## 文脈

usage-hint の値は、次の 2 つのときにだけ変わる ([ADR 0004](0004-usage-hint-mod.md), [0008](0008-usage-hint-initial-values.md))。

- セッションを開いたとき (`session.start`): `$.session.usage()` の値と、前回保存したレートリミットの窓から作る。
  リセット時刻を過ぎた窓は 0% にする。
- API の応答を受けたとき (`session.measure`)。

そのため、何も送らずにセッションを開いたままにしていると、レートリミットの窓のリセット時刻を過ぎても、古い使用率
(と 75%・90% を超えた色。[ADR 0060](0060-usage-hint-danger-color.md)) が出たままになる。本人から、アクティブなセッションに限り
1 分に 1 回、表示の値を更新し、セッションを開いたときにも同じ更新をしたいと要望があった
(`/usage-hint` コマンドや組み込みの `/usage` を実行するのではなく、表示の値を更新することを確かめた)。

調べた結果は次のとおり。

- `$.session.usage()` は、ステータスラインと同じ値 (コンテキスト・レートリミットの窓・費用) を返し、引数無しの呼び出しは費用がかからない
  (トークン数の API を使わない)。
- `$.clock.every(ms, fn)` は、`cancel()` するまで `ms` ごとに `fn` を呼ぶ。テストでは `mock.clock` の `advance` で時計を進められる。
- 更新の処理を入力欄の描画などから行うと、描くたびに走る。時計で行えば、セッションが開いている間だけ動く
  (セッションのプロセスが終われば止まる)。
- mod の API には、端末やウィンドウが前面にあるか (フォーカス) を知る手段が無い。使えるのは、セッションを表示している画面の一覧
  (`$.session.surfaces()`。`terminal`・`desktop`・`mobile`・`vscode`) と、入力・応答の時刻。本人は「アクティブ」を
  「画面に表示中」(画面の一覧が空でない) とすることにした。端末で動かしているセッションは、端末が表示しているので、
  開いている間は常に表示中と扱われる見込み (デスクトップ・スマートフォンから離れたセッションは止まる)。

## 実装すること

- 表示の値を更新する処理 (`refresh`) を作る。
  - `$.session.usage()` を読み、レートリミットの窓が空でなければそれを、空なら直前の表示の窓を使う。
  - どちらの場合も、リセット時刻を過ぎた窓は使用率 0・次のリセット時刻は不明にする (今の `restoreLimits`)。
  - コンテキストの使用率は、`usage().context.percent` があればそれを、無ければ直前の値を使う。
  - 読み取りに失敗したときは、直前の表示を残す。
- `session.start` で、今の開始時の処理 (前回保存した窓・コンテキストの推定) の後に `refresh` を 1 回行い、`$.clock.every(60_000, …)` を始める。
- 1 分ごとの処理では、`$.session.surfaces()` が空のとき (どの画面も表示していない) は `refresh` を行わない。
  表示に戻れば、次の 1 分ごとの処理から再び更新する。読み取りに失敗したときも行わない。
- `session.end` で、時計を止める (`cancel()`)。
- 保存 (`$.store`) は今どおり `session.measure` だけで行う (`refresh` は保存しない)。
- `docs/specifications.md` の usage-hint の節に書く。

## 実装しないこと

- 組み込みの `/usage` を実行すること (実行のたびに会話の履歴に行が残る)。
- 1 分の間隔を設定で変えられるようにすること。
- サーバーにレートリミットを問い合わせること (`$.session.usage()` の値と時計だけで更新する)。

## テスト設計

`tests/start.test.tsx` (または新しいテストのファイル) に、`mock.clock` で時計を進めるテストを足す。先に書いて失敗させてから実装する。

- 開始の 1 分後に、`session.usage` が返す新しい窓の値が表示に出ること。
- 開始の後に窓のリセット時刻を過ぎると、1 分以内の更新でその窓が `0%` になり、色が `normal` (dim) に戻ること。
- `session.usage` の窓が空のときは、直前の表示の窓が残ること (リセット時刻を過ぎたものだけ `0%`)。
- 1 分たたないうちは更新しないこと (`session.usage` の呼び出しの回数で確かめる)。
- `session.surfaces` が空の間は、時計を進めても `session.usage` を呼ばず、空でなくなると次の 1 分で更新すること。
- `session.end` の後は、時計を進めても `session.usage` を呼ばないこと。
- 既存のテストがすべて通ること。`tsc --noEmit -p .` がエラー 0 で終わること。

## トレードオフ

- 表示中のセッションごとに、1 分に 1 回 `$.session.usage()` を呼ぶ (費用はかからないが、セッションの数だけ動く)。
  端末のセッションは、tmux の裏のウィンドウにあっても表示中と扱われるので、開いている端末のセッションはすべて動く見込み。
- 表示しているかの確認 (`$.session.surfaces()`) は、表示していないセッションでも 1 分ごとに行う。
- 表示の更新は最大 1 分遅れる (リセット時刻の直後は、最大 1 分古い値が出る)。
- 窓がリセットされた後の 0% は推定で、実際の使用率は次の API の応答まで分からない ([ADR 0008](0008-usage-hint-initial-values.md) と同じ扱い)。
