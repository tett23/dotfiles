# ADR 0125: ロードマップの書き方をそろえる roadmap スキルを足す

Status: proposed

## 文脈

本人から、リポジトリのロードマップ (`docs/roadmap.md`) の書き方を全リポジトリでそろえるよう頼まれた。
手本は Golem の今の `docs/roadmap.md` で、新しいスキルとして作る。
項目は、実装されるまで残す。
これは、Golem の「実装を終えたら項目を消し、振る舞いを仕様書に書く」と同じ意味である (本人に確かめた)。

`close-reading` スキルは、ロードマップを拠りどころの文書の一つに数え、「ロードマップ（あれば）」として読む。
しかし、ロードマップを書くときの決まりは、どのスキルにも無い。

新しいスキルを dotfiles で管理することと [ADR 0118](0118-split-instructions-into-skills.md) の関係は、[ADR 0123](0123-context-restore-skill.md) の「文脈」と同じである ([ADR 0118](0118-split-instructions-into-skills.md) の「実装しないこと」は、新しく作るスキルを指さない)。

## 調査した事項

Golem (`tett23/golem`、`docs/roadmap.md` を最後に変えたコミットは `85bc0377`、2026-11-11) の `docs/roadmap.md` (305 行) を読んだ。

- 冒頭の段落は、次のことを書く。
  - 今の振る舞いは仕様書に書き、ロードマップには書かない。バージョンごとの節に載る項目は、どれもまだ無い。
  - ほかに、「手で確かめる項目」「未決事項」「課題にしなかった事項」もまとめる。
  - どの項目も、着手するときに ADR を作る。採択した ADR があり、まだ実装していない項目には「（未実装）」と書き、その ADR へリンクする。
  - 実装を終えたら、その項目を消し、振る舞いを仕様書に書く。
- 節の並びは次のとおりである。
  - 「リリースの予定」: 次に出す版と、その後の予定。今の時点の計画で、変わりうると書く。
  - 版ごとの節 (「v0.1.0-rc4」「v1.0.0」「v1.x」など) と、先に回した事項の節 (「v2 以降に回した事項」など)。
    扱う項目をすべて実装した版の節は、「…で扱う項目は、すべて実装した。」の一文だけを残す。
    版の節は、主題ごとの小見出しに分けてよい。項目は上から順に実装できるように並べ、ほかの項目に依る項目は、その項目の後に置く。
  - 「手で確かめる項目」: 実装と自動のテストは終わったが、ADR が求める手作業の確かめが残っている項目。確かめたら、結果を残し、一覧から消す。
  - 「未決事項」: 決まっていない事項。決めたら、仕様書か ADR に書き、一覧から消す。
  - 「課題にしなかった事項」: 扱わないと決めた事項。扱う必要が出たら、新しい ADR で決め直す。
- 「リリースの予定」は、版の付け方を仕様書の「バージョン」の節へリンクで引く (16 行)。
- 時期を決めていない節 (「v3 より前（時期は未定）」、193 行) もある。
- 「手で確かめる項目」は、確かめた結果を「実装のプルリクエストか `docs/audits/` の記録」に書くとしている (216 行)。
- 「未決事項」は、v1 より後の版のための事項に、その版を書くとしている (249 行)。
- 項目は、「- **<名前>**：<説明>」の形の箇条書きである。説明の下に、入れ子の箇条書きを使う項目もある (42〜45 行、82〜90 行)。説明には、理由、ほかの項目との順序、関係する ADR へのリンクを書く。
  確かめる時期があるときは、名前の後に「（v1.0.0 のリリースで確かめる）」のように添える。
- dotfiles には `docs/roadmap.md` が無い。

## 実装すること

- `agents/skills/roadmap/SKILL.md` を作る。中身は、上の Golem の決まりを、どのリポジトリでも使える形にしたものである。
  - 置き場所: `docs/roadmap.md`。モノレポでモジュールごとに持つときは `docs/<module name>/roadmap.md`。
  - 冒頭の段落に書くこと: 仕様書との分担 (今の振る舞いは仕様書、まだ無いものはロードマップ)、載せる節の種類、ADR との関係、項目を消すとき。
  - 節: 「リリースの予定」、版ごとの節と先に回した事項の節、「手で確かめる項目」、「未決事項」、「課題にしなかった事項」。
    - 「リリースの予定」は、版の付け方を仕様書の該当の節へのリンクで引く。
    - 時期を決めていない版の節 (「v3 より前（時期は未定）」など) を置いてよい。
    - 版の無いリポジトリでは、版ごとの節の代わりに「扱う事項」の一つの節にしてよい。
    - 扱う項目をすべて実装した版の節は、「<版> で扱う項目は、すべて実装した。」の一文だけを残す。
    - 「手で確かめる項目」「未決事項」「課題にしなかった事項」は、項目が無いときは節を置かない。
  - 項目の形: 「- **<名前>**：<説明>」。説明に、理由、順序、関係する ADR へのリンクを書く。説明の下に、入れ子の箇条書きを使ってよい。確かめる時期や対象の版があるときは、名前の後に「（v1.0.0 のリリースで確かめる）」のように添える。未決事項のうち、次に出す版より後の版のための事項には、その版を添える。Golem は「v1 より後」の事項にだけ版を書いており (249 行)、この決まりは Golem から広げたものである。
  - ADR との関係: 着手するときに ADR を作る。`accepted-pending` の ADR がある項目には「（未実装）」と書き、ADR へリンクする。`superseded-pending` の ADR がある項目にも「（未実装）」と書き、元の ADR と修正先の ADR へリンクする。修正先の無い注記 (`kind` が `note`) だけのときは、元の ADR へリンクする。
  - 項目を消すとき: 実装を終えるまで項目を残す。実装を終えたら、同じ変更で、項目を消し、振る舞いを仕様書に書く。
    手で確かめる項目は、確かめた結果を実装のプルリクエストか `docs/audits/` の記録に書いた後に消す。未決事項は、決めたことを仕様書か ADR に書いた後に消す。
  - 並べ方: 上から順に実装できるように並べ、ほかの項目に依る項目は後に置く。
- `flake.nix` の `home.file` で、`agents/skills/roadmap` を `~/.claude/skills/roadmap` と `~/.agents/skills/roadmap` にリンクする ([ADR 0118](0118-split-instructions-into-skills.md) と同じ形)。
- 共通の指示 (`.claude/CLAUDE.md`、`codex/AGENTS.md`) の「スキル」の表に、`roadmap` の行を足す。使うときは「ロードマップを書く前、直す前。項目の実装を終えた後、手で確かめた後、未決事項を決めた後で、その項目をロードマップから消す前」、使いかたは「節と項目の形に従い、実装を終えた項目は消して仕様書に書く」とする。この表は [ADR 0127](0127-skills-table-in-shared-instructions.md) で置く。
- `docs/specifications.md` のリンクの表と Claude Code の節に書く。README は変えない。

## 実装しないこと

- dotfiles に `docs/roadmap.md` を作ること。
- Golem の `docs/roadmap.md` を、このスキルに合わせて書き直すこと。
- ロードマップの形を、CI などで機械的に検査すること。

## 不変条件

なし。文書の書き方の決まりと、リンクの設定だけを決める ADR で、入力に対する振る舞いを決めない。

## 受けいれ条件

- A1: `agents/skills/roadmap/SKILL.md` に、「実装すること」の決まりがすべて書いてある。
- A2: Golem の今の `docs/roadmap.md` の決まり (冒頭の段落、節の並び、項目の形、項目を消すとき) は、すべてスキルの決まりのどれかに当たる。
- A3: Claude Code と Codex の新しいセッションで、スキルの一覧に `roadmap` が出る。
- A4: 共通の指示の両方のファイルの「スキル」の表に `roadmap` の行が同じ文であり、`docs/specifications.md` のリンクの表に `roadmap` がある。

## テスト設計

文書の決まりなので、CI の自動のテストは書かない。

- A1: 実装の後に、スキルを「実装すること」の各項目と突き合わせ、`close-reading` で精読する。
- A2: Golem の `docs/roadmap.md` の冒頭の段落と各節の頭の段落を一つずつ読み、スキルのどの決まりに当たるかの表を作る。当たらないものがあれば、スキルに足す。
- A3: 本人が `sudo darwin-rebuild switch --flake ~/dotfiles#dione` を実行した後に、`~/.claude/skills/roadmap` と `~/.agents/skills/roadmap` のリンクと、Claude Code と `codex exec` のスキルの一覧を確かめる。
- A4: 両ファイルの「スキル」の節を切り出して `diff` し、差分が無いことを確かめる。`grep -n roadmap docs/specifications.md` でリンクの表を確かめる。

## トレードオフ

- Golem の決まりを手本にするので、版のあるリポジトリに向いた形になる。版の無いリポジトリは、版ごとの節を一つにまとめる。
- 実装を終えた項目を消すので、ロードマップには何を終えたかが残らない。終えたことは、仕様書と ADR と Git の履歴で追う。
