# 精読モード

文書を段に分けて読み、読み手の役を割り当て、指摘を根拠つきで一つの形にまとめる手順である。
出版の校正（文字と形の誤り）と校閲（内容の誤りと矛盾）の区別、Fagan インスペクションの段の分け方、視点による読み（PBR）を下敷きにする。
文献の要約は、このスキルの `research.md` にある。
Claude Code でも Codex でも使える。
サブエージェントが使えない環境では、「サブエージェントへの分担と統合」の節を、一人で順に読む手順として読み替える。

## 約束

- **報告までで止める。**
  文書を直すのは、メンテナーが求めたときだけである。
  直すときも、コミット済みの ADR はステータスの行とリンクのほかを書き換えない（変えたいときは新しい ADR を提案する）。
  `docs/audit/`、`docs/audits/`、`docs/benchmarks/`、`docs/benchmark/` の記録は変えない。
- **根拠のない指摘を出さない。**
  どの指摘にも、問題の箇所の引用と、根拠の file:line を付ける。
  根拠を見つけられなかった事柄は、欠陥ではなく「確認事項」として分けて出す。
- **全文を読む。**
  grep の結果だけで判断しない。
  grep とツールは候補を拾う道具であり、指摘にする前に前後の文脈を読む。
- **基準の版を固定する。**
  読む前に、どのコミットを読むかを決めて報告に書く（`git rev-parse HEAD`）。
  プルリクエストのレビューなら、ベースとヘッドの両方を書く。
- **書くときの規則は、指摘の文にも当てはまる。**
  報告も一文一行で書き、ダッシュと並列の中黒を使わない。

## 使う場面と使わない場面

使う場面は次のとおりである。

- マニュアルの章や付録を丸ごと読む（素読み）。
- マニュアル、仕様書、ADR を変えるプルリクエストの差分を読む（突き合わせ）。
  前の版との違いと、前のレビューで指摘した箇所が直ったか（赤字合わせ）を確かめる。
- 提案の ADR（`adr-guard proposed --status` で一覧できる）を採択の前に読む。
- ADR を書いた後に、仕様書、README、ほかの ADR との食い違いを確かめる。
- 仕様書とロードマップ（あれば）とマニュアルのあいだの食い違いを洗い出す。

使わない場面は次のとおりである。

- コードの正しさのレビュー（コードレビューのスキルを使う）。
- 文書を新しく書く作業（`doc-writing` スキルがあればそれを、なければ全リポジトリ共通の指示の「文書の書き方」に従う）。

## 拠りどころの文書と優先順位

精読の基準にする文書と、食い違ったときの扱いを先に決めておく。

最初に、そのリポジトリにどの文書があるかを確かめる。

```sh
$ git ls-files | grep -iE '(^|/)(README|CONTRIBUTING|CLAUDE|AGENTS|glossary|roadmap|specifications|diagnostics)[^/]*$'
$ ls docs docs/adr 2>/dev/null
$ git ls-files | grep -iE 'manual|policy|style'
```

あったものを次の表の行に当てはめる。
なかった行は飛ばし、報告の冒頭に「このリポジトリにない基準」として書く。

| 文書 | 何の基準か |
| --- | --- |
| コードとテスト | 今の振る舞いの事実。事実の確認の一次資料 |
| `docs/specifications.md`（モジュールごとに `docs/<モジュール>/specifications.md` があればそれも） | 今の振る舞いの記述 |
| ロードマップ（`docs/roadmap.md` など、あれば） | まだない項目、手で確かめる項目、未決事項。仕様書には書かない |
| ADR（`docs/adr/` など。モジュールごとの `docs/<モジュール>/adr/` があればそれも） | 決定の記録。ステータスの行で効力が決まる。後の ADR が前の ADR を変える |
| README | 初めての読み手への入口。仕様書と食い違わない |
| マニュアルとその方針の文書（`docs/manual-policy.md` など、あれば） | マニュアルの読み手、文体、言葉の選び方、章立て。ADR と食い違うときは方針の文書に従う |
| `CONTRIBUTING.md`、リポジトリの CLAUDE.md、AGENTS.md | 文章の規則、文書の更新の決まり |
| 用語集（`docs/glossary.md` など、あれば） | 用語の意味 |
| 診断やエラーコードの一覧（`docs/diagnostics.md` など、あれば） | コードと重大度 |

文書の書き方の基準は、全リポジトリ共通の指示（CLAUDE.md または AGENTS.md の「文書の書き方」、または `doc-writing` スキル）である。
リポジトリに固有の規則がそれと食い違うときは、リポジトリの規則に従い、食い違いを報告に書く。

仕様書の記述とコードが合わないときは、どちらが正しいかをこのモードでは決めない。
関係する ADR を示し、「仕様書とコードが合わない」という一つの指摘として出す。
マニュアルには採択して実装を終えた仕様だけを書く決まりがあるなら、マニュアルがロードマップの項目を今の機能として書いていれば指摘する。

## 読みの段

段は順に進める。
各段で作るもの（構造の表、用語の台帳、主張の表）は、次の段と、文書間の段で使う。

### 段 0：範囲と基準を決める

1. 読むコミットを決める（`git rev-parse HEAD`、プルリクエストなら `git merge-base origin/main HEAD` も。既定のブランチが main でなければ読み替える）。
2. 読む文書を並べる。
   マニュアルが複数の章に分かれているなら、目次かマニフェスト（章の順を定めるファイル）の順に並べる（読み手が読む順であり、定義より前の使用はこの順で判断する）。
   目次がなければファイル名の順にする。
3. 読み方を決める。
   丸ごと読むなら素読み、差分なら突き合わせとし、突き合わせでは `git diff <ベース>...<ヘッド> -- <文書>` を読む。
4. 文書の種類から、割り当てる視点を決める（「視点」の節）。

### 段 1：構造を通読する

本文の細部に入る前に、見出しと段落の並びだけを読む。

- 見出しの一覧を作る。
  Markdown は行頭の `#` で見出しを書く。
  他の形式の原稿（AsciiDoc、独自記法など）は、その形式の見出しの書き方に合わせる。

  ```sh
  $ grep -nE '^#{1,4} ' docs/specifications.md
  $ for f in $(git ls-files 'docs/**/*.md'); do grep -nE '^#{1,4} ' "$f" | sed "s|^|$f:|"; done
  ```

- 見出しの段が飛んでいないか（`#` の次に `###` が来ていないか）。
- 決まった章立てと合っているか。
  マニュアルは方針の文書の章立て（あれば）と、ADR は全リポジトリ共通の指示の構成（ステータス、文脈、実装すること、実装しないこと、不変条件、テスト設計、トレードオフ、参考文献）と比べる。
- 一つの節が二つの話題を持っていないか、同じ話題が二つの節に散っていないか。

### 段 2：用語の台帳を作る

文書に出る用語を、出る順に台帳へ記録する。

| 語 | 最初に出る箇所 | 説明している箇所 | 説明の形 | 同じものを指す別の語 |
| --- | --- | --- | --- | --- |
| フォントの役割 | manual/chapters/03-markup.md:12 | manual/chapters/05-style.md:40 | 定義文 | 書体の役割（揺れ） |

上の行は書き方の例であり、実際の箇所ではない。

台帳に載せる語は、分野の術語、そのリポジトリ固有の語（プロダクトやモジュールの名前、設定の単位など）、略語、外来語、コマンド、オプション、ファイルの名前、診断やエラーのコードである。
台帳から次を拾う。

- **定義より前の使用**：最初に出る箇所が、説明している箇所より前にある。
  章の順は段 0 の並びで判断する。
  方針の文書に「言葉の選び方」の表（語と最初の説明の箇所）があれば、その表のとおりかを一語ずつ確かめる。
- **未定義の語**：説明している箇所がない。
  読み手の知識の前提（方針の文書があればそれに、なければ文書の種類ごとの読み手に従う。マニュアルは初めて触れる人、仕様書と ADR は会話の文脈を持たない人）で、説明が要るかを判断する。
- **揺れ**：同じものを二つの語で呼んでいる。
  用語集があれば、その見出し語と比べる。
- **一語多義**：一つの語を二つの意味で使っている（「版」を version と edition の両方に使う、など）。
- **用語の一覧への漏れ**：新しい語が用語集（あれば）にない。

### 段 3：主張を確かめる

文書の中の、事実として確かめられる主張を拾い、一つずつ一次資料と照らす。
拾う主張は次のとおりである。

- コマンド、オプション、その既定値、終了コード
- ファイルとディレクトリのパス、設定ファイルのキーと既定値
- 診断やエラーのコードと重大度、メッセージ
- 振る舞いの記述（何をする、何をしない、どの出力が何を読む）
- 数（字数、行数、上限、個数）
- ADR の番号とその内容の要約、リンク先の節の題
- ライセンス、外部の規格の名前、URL

確かめ方は次のとおりである。
ソースのディレクトリは、リポジトリにあるものに置き換える（`src/`、`lib/`、`modules/` など）。

```sh
$ git grep -n '<識別子やキー>' -- <ソースのディレクトリ> scripts/
$ git grep -n '<診断のコード>' -- <ソースのディレクトリ> docs/
$ <実行ファイル> --help   # 実行ファイルがあれば、ビルドして --help の出力と照らす
```

主張ごとに、次の三つのどれかに分ける。

- **一致**：根拠の file:line を控える。報告には出さない。
- **不一致**：文書の箇所と、食い違うコードか文書の箇所を両方示して指摘する。
- **確認できない**：根拠を探した範囲（検索した語とディレクトリ）を書いて、確認事項に回す。

推測で「おそらく正しい」「おそらく誤り」としない。

### 段 4：文書どうしを照らす

一つの文書の中では見えない食い違いを探す。
段 2 の台帳と段 3 の主張の表を、文書をまたいで突き合わせる。
リポジトリにない文書に関する項目は飛ばす。

- **仕様書とロードマップ**：実装を終えた項目がロードマップに残っていないか。
  ロードマップの項目（まだない機能）を、仕様書が今の振る舞いとして書いていないか。
- **仕様書と ADR**：仕様書が引く ADR のステータスが採択か。
  後の ADR に変えられた ADR の古い決定を、仕様書が書いていないか。
  ステータスは `adr-guard list --status` で一覧できる。
- **仕様書と README**：README が、仕様書と違う振る舞いや、古いコマンドを書いていないか。
- **仕様書とマニュアル**：マニュアルが、仕様書と違う振る舞いを書いていないか。
  マニュアルが複数あれば（使い手向けと開発者向けなど）、同じ事柄の書き方が食い違っていないか。
  文書が変わったかどうかだけを見る検査（リポジトリにあれば）は中身のずれを拾わないので、中身のずれはここで探す。
- **マニュアルと方針の文書**：方針の文書が決めた章立て、付録、言葉の選び方に従っているか。
- **診断やエラーの一覧**：一覧の文書のコードと、仕様書、マニュアルの付録、コードの定義が一致するか。
- **参照**：相対リンクの先のファイルがあるか、アンカーの見出しがあるか、ADR の参照にリンクが付いているか（`adr-guard links`）、マニュアルの相互参照の先のラベルがあるか（マニュアルの検査コマンドがあればそれで）。

### 段 5：言葉を読む

表記の規則は、先にツールと grep で候補を拾い（「ツール」の節）、候補の前後を読んで判断する。
そのうえで、ツールでは拾えない翻訳調、曖昧さ、論理の飛躍を読む。

#### リポジトリの表記の規則

最初に、そのリポジトリの文章の規則がどこに書かれているかを探す。
候補は `CONTRIBUTING.md`、CLAUDE.md、AGENTS.md、マニュアルの方針の文書、textlint や prh の設定である。
見つけた規則を表にして、報告の冒頭に「適用した規則」として書く。
見つからなければ、全リポジトリ共通の指示の「文書の書き方」と、次の既定の規則だけを使う。

- 一文ごとに改行する。リストの項目と表のセルは例外で、一つの項目に複数の文を書いてよい。
- 地の文で、ダッシュ（——）と、並列を表す中黒（・）を使わない。並列以外の中黒（外来語の区切りなど）は使ってよい。

規則が適用される範囲に注意する。
リポジトリが「この日付以降に書く文書に適用する」と定めているなら、それより前の文書の表記は指摘しない。
コミット済みの ADR は直さないので、既存の ADR の表記は指摘しない。

リポジトリに規則の表がある場合は、次の形に整理して使う。

| 規則 | 対象 | 拾い方 |
| --- | --- | --- |
| 敬体（です、ます）で書く | 規則が定める文書（例：使い手のマニュアル） | textlint の `no-mix-dearu-desumasu` |
| 常体（である）で書く | 規則が定める文書（例：開発者のマニュアル） | 同上 |
| 特定の語を別の語に統一する（例：資産→アセット、機械→マシン） | 規則が定める文書 | `grep -n '<語>'` の後に文脈で判断 |
| 本文に出さないもの（例：ADR の番号、内部の型の名前） | 規則が定める文書 | `grep` で候補を拾う |
| ファイル名、コマンド、パス、キーの書き方（例：コードの記法で囲む） | 二冊とも | `grep` で候補を拾う |
| コマンドの行の書き方（例：`$` と空白で始め、出力と続きの行には付けない） | 全文書 | コードブロックを読む |
| 説明していない語をいきなり使わない | 全文書 | 段 2 の台帳 |

規則の本体は、方針の文書など元の文書にある。
この表と元の文書が食い違ったら、元の文書に従い、この表の古さを報告に書く。

#### 翻訳調

英語の構文をなぞった文を拾う。
言い換えの候補を添えて指摘する。

- 「〜することができる」：「〜できる」で足りる。
- 「〜を持つ」（have の直訳）：「〜がある」「〜を含む」で足りないかを見る。
- 無生物を主語にした他動詞の文（「この設定はエラーを引き起こす」）：日本語として自然な主語に直せるかを見る。
- 受け身の多用（「〜される」が続く）。
- 「〜において」「〜に関して」「〜に対して」の多用。
- 代名詞（「それ」「これ」「その」）：指す先が直前の一つに決まるか。
- 「X（Yの）」のように、括弧で語の意味を補う書き方（過去の直しで除いた形が、リポジトリの履歴にあれば参照する）。

#### 曖昧さ

一文から二通りの読みが作れるかを問う。
二通りの読みを両方書いて指摘する。

- 数量の語：「すべて」「各」「どれも」「一つ」の範囲。
- 限定の語：「だけ」「のみ」「も」がどこに係るか。
- 「など」「ほか」：何を含み、何を含まないか。
- 「かつ」「または」「と」：組み合わせの結合の強さ（A と B または C）。
- 否定の範囲：「A と B を検査しない」は両方か片方か。
- 境界：「以上」「超える」「まで」「以内」、ページや行の数え始め。
- 条件：「場合」と「とき」の入れ子、条件が満たされないときの振る舞いが書かれているか。
- 連体修飾の係り先：「このツールが読む設定のファイル」は何が何を読むか。

仕様書と ADR では、加えて「この文からテストを一つ書けるか」を問う。
書けない文は、検証できない記述として指摘する。

#### 論理の飛躍

- 「〜のため」「〜ので」の理由が、主張を支えているか。
- 前提が書かれずに結論だけがあるか。
- 「常に」「必ず」「決して」が、例外を書いた別の箇所と矛盾していないか。
- 手順の途中の段が抜けていないか（読み手がその手順だけで目的に着けるか）。

### 段 6：報告を書く

「報告の形」の節に従う。

## 視点

視点による読み（PBR）にならい、読み手の役を割り当てる。
役ごとに「その役としてこの文書から作るもの」を課し、作れなかった箇所を指摘にする。

| 視点 | 主に読む文書 | 作るもの | 問い |
| --- | --- | --- | --- |
| 初めての利用者 | マニュアル、README | 導入から最初の成果物を得るまでの手順 | 手順だけで最初の成果物まで着けるか。説明なしに出る語がないか。前提の知識が書かれているか |
| 分野の専門家（リポジトリの分野に応じて割り当てる） | マニュアル | その分野の実務の手順（例：組版のプロダクトなら、編集者、DTP オペレーター、著者が、原稿から入稿のデータまでを作る） | 分野の術語が業界の使い方と合っているか。実務の手順と合うか。ツール自身が判定できず、別のツールが要る範囲が書かれているか |
| 開発者 | 開発者向けのマニュアル、仕様書、ADR | 拡張の最小の実装、または変更のための手順 | モジュールと型の名前、ビルドとテストのコマンドがコードと合うか。ADR の決定と仕様書の記述が一致するか |
| テストを書く人 | 仕様書、ADR | 仕様の一節ごとのテストのケース | 一文ごとにテストを書けるか。境界と、条件を満たさないときの振る舞いが書かれているか |

利用者向けの文書（マニュアル、README）には初めての利用者と、分野に応じた専門家の役を、開発者向けの文書には開発者を、仕様書と ADR には開発者とテストを書く人を割り当てる。
分野の専門家の役は、方針の文書か README に書かれた読み手から決める。
視点ごとに見つけたものは、「視点」の欄に記録する。

## ツール

使う前に、そのマシンにあるものを確かめる。

```sh
$ for c in adr-guard textlint git grep rg; do command -v "$c" >/dev/null && printf '%s: あり\n' "$c" || printf '%s: なし\n' "$c"; done
$ ls scripts scripts/* 2>/dev/null | head -50
```

`adr-guard`、`textlint`（プリセット、規則、設定が入っているかも確かめる）、`git`、`grep` と、リポジトリのスクリプト、リポジトリのビルドの成果物が使える。
これら以外のツール（textlint のプリセット、prh、markdownlint-cli2、lychee など）を入れること、`npx --yes` で取得して走らせること、`package.json` や `.textlintrc` をリポジトリに足すことは、メンテナーの承認を得てから行う。
承認がない間は、grep の手順で代える。

### いまあるもので走らせる

リポジトリにあるものだけを走らせる。
走らせたもの、走らせなかったものとその理由を、報告の冒頭に書く。

```sh
# ADR のステータスの行と、リンクのない ADR の参照（--fix は付けない）
$ adr-guard check-status
$ adr-guard links
$ adr-guard proposed --status

# リポジトリの検査用スクリプト（あれば）。文書が参照する文書の一覧、
# 仕様書を変えたブランチがマニュアルも変えたか、マニュアルの構文と参照の検査など
$ ls scripts/ci scripts/manual scripts/docs 2>/dev/null
```

スクリプトの中身を読み、何を検査するかを確かめてから走らせる。
時間のかかるもの（文書全体のビルドなど）は、主張の確認に要るときだけ走らせる。

### grep で表記の候補を拾う

macOS の grep で動くことを確かめた形である（`LANG=ja_JP.UTF-8`）。
拾ったものは候補であり、指摘にする前に前後を読む。
対象のディレクトリと拡張子は、リポジトリに合わせて置き換える。

```sh
# ダッシュ
$ grep -rnE '—|―' docs README.md --include='*.md'
# 中黒（並列のほか、外来語の区切りや記号の名前もあるので一つずつ判断する）
$ grep -rn '・' docs README.md --include='*.md'
# 一行に二文以上（リストの項目と表の行はここで除いている）
$ grep -rnE '。[^）」』|]' docs README.md --include='*.md' | grep -vE '^[^:]+:[0-9]+:[[:space:]]*([-*|]|[0-9]+\.)'
# リポジトリの用語の規則（語はリポジトリの規則から決める）
$ grep -rnE '<語1>|<語2>' <文書のディレクトリ>
```

Markdown の相対リンクの先のファイルがあるかは、次で確かめる。
アンカー（`#版` のような見出しへのリンク）は、リンク先の文書の見出しを grep で探して確かめる。

```sh
$ for f in $(git ls-files 'docs/*.md' 'docs/**/*.md' README.md CONTRIBUTING.md); do
    d=$(dirname "$f")
    grep -oE '\]\([^)#:]+(#[^)]*)?\)' "$f" | sed -E 's/^\]\(//; s/\)$//; s/#.*//' | while read -r p; do
      [ -z "$p" ] || [ -e "$d/$p" ] || printf '%s: %s\n' "$f" "$p"
    done
  done
```

この手順は、インラインのコードとコードブロックの中のリンクの形も拾う。
たとえば、ADR が別の ADR に書き足すステータスの行を `` `採択→…は [ADR 0009](0009-ruby-placement.md)` `` のように引いていると、引いた先の文書から見た相対パスなので、ここでは壊れて見える。
拾ったものは、その行を開いて地の文のリンクかを確かめてから指摘にする。

### textlint（承認を得てから）

承認を得たら、次の形を勧める。
規則の候補は MIT の npm パッケージで、入れた後は通信せずに動く。

| パッケージ | 拾うもの |
| --- | --- |
| `textlint-rule-preset-ja-technical-writing` | 長い文、読点の多さ、二重助詞、ですますとであるの混在、冗長な表現、半角カナ、対にならない括弧 |
| `textlint-rule-preset-ja-spacing` | 全角と半角のあいだの空白（リポジトリが空白を入れる表記なら、`ja-space-between-half-and-full-width` を `always` にする。入れない表記なら `never`） |
| `@textlint-ja/textlint-rule-preset-ai-writing` | LLM が書きがちな空句と誇張 |
| `textlint-rule-prh` | プロジェクトの用語の辞書（下の例） |

`textlint-rule-preset-jtf-style` は、全角と半角のあいだに空白を入れない規則を持つ。
リポジトリの表記が空白を入れるものなら衝突するので、丸ごとは入れない。

独自記法の原稿（Markdown 以外）には記法の括弧があり、平文として読ませると対にならない括弧の誤検知が出る。
次のどちらかで渡す。

- 原稿をプレーンテキストに書き出せるツールがあれば、その出力を渡す。
  位置は原稿と合わないので、指摘の文を `grep -rnF` で原稿から探して file:line を付け直す。
- `@textlint/textlint-plugin-text` の `extensions` にその拡張子を足して原稿を直接渡し、`no-unmatched-pair` を切る。

prh の辞書の例（文書の種類ごとに分ける）。
語はリポジトリの規則から決める。

```yaml
# developer-manual.prh.yml（開発者向けのマニュアルの例）
version: 1
rules:
  - expected: アセット
    pattern: 資産
```

```yaml
# user-manual.prh.yml（利用者向けのマニュアルの例）
version: 1
rules:
  - expected: フォルダ
    pattern: /(?<!「)ディレクトリ/
```

文脈でしか決まらない語（同じ語を文書ごとに別の語に直す場合など）は辞書に入れず、段 5 で読む。

## サブエージェントへの分担と統合

サブエージェントを起動できない環境では、分担を一人で順に行う。
その場合も、読み手の役と統合の手順は省かない。

### 分け方

親のエージェントはまとめ役（Fagan のモデレーター）を務め、自分では段 0 と段 6 と、指摘の検証を受け持つ。
読む作業は、文書の範囲と段で分けてサブエージェントに渡す。

- **文書の読み手**（文書の範囲ごとに一体）：段 1、段 2、段 3、段 5 を受け持つ。
  マニュアルは前半の章、後半の章、付録の三つほどに分ける。
  開発者向けのマニュアルは部ごとに、仕様書は節のまとまりで分ける。
  視点を一つか二つ割り当てる。
- **文書間の読み手**（一体）：段 4 を受け持つ。
  文書の読み手が出した用語の台帳と主張の表を入力に受け取り、文書をまたいで照らす。
  文書の読み手が終わってから走らせる。
- **ツールの係**（一体、または親が自分で）：「ツール」の節のコマンドを走らせ、出力をそのまま返す。

サブエージェントは読むだけにする（読み取り専用の探索用の役割、または書き込みを指示しない汎用の役割）。
各サブエージェントへの指示には、次を必ず含める。

1. 読むコミットと、読むファイル（行の範囲があれば範囲も）
2. 受け持つ段と視点
3. このスキルの「拠りどころの文書と優先順位」「段 5 の表記の規則」の要点（そのリポジトリで見つけた文書と規則）
4. 報告の形（下の「報告の形」の一件の形）と、根拠のない指摘を出さないこと、確かめられないものは確認事項に回すこと
5. 用語の台帳と主張の表も返すこと（文書間の読み手が使う）
6. ファイルを書かないこと

### 統合の手順

1. **形をそろえる**：すべての指摘を一件の形に直す。
   形を満たさない指摘（引用か根拠がない）は、サブエージェントに問い直すか、捨てる。
2. **引用を確かめる**：引用が原文のとおりかを `grep -nF '<引用>' <ファイル>` で確かめる。
   一致しない指摘は、位置を直すか捨てる。
3. **重複をまとめる**：同じ箇所の同じ種類の指摘は一つにする。
   同じ原因（ある語の定義の欠け、ある仕様の変更の反映漏れ）から出た複数の箇所の指摘は、一件にまとめて位置を並べる。
4. **根拠を確かめる**：重大度が高の指摘は、親が根拠の file:line を自分で開いて読む。
   中と低の指摘は、少なくとも三件に一件を抜き出して読む。
   根拠が主張を支えていなければ、確認事項に下げるか捨てる。
5. **重大度を付け直す**：サブエージェントの付けた重大度を、下の基準でそろえる。
6. **ツールの結果と照らす**：ツールが拾い、読み手が拾わなかったものを足す。
   読み手が拾い、ツールが拾わなかった表記の指摘は、ツールの規則に足せるかをメモする。

### 重大度

| 重大度 | 基準 |
| --- | --- |
| 高 | 読み手が誤った操作や判断をする。文書とコードが食い違う。規範の文書どうしが矛盾する。参照が壊れていて辿れない |
| 中 | 定義より前の使用、未定義の語。二通りに読める文。文書間の古い記述。テストを書けない仕様の文 |
| 低 | 表記の規則への違反、翻訳調、揺れのうち意味を取り違えないもの |
| 確認事項 | 根拠を探したが確かめられなかったもの。どちらが正しいかを決めるのにメンテナーの判断が要るもの |

## 報告の形

報告は会話に返す。
リポジトリにファイルとして書かない。
記録として残すよう求められたときだけ、`docs/audits/` に新しいファイルとして置く（コミットした後は変えられない）。

### 冒頭のまとめ

```markdown
# 精読の報告

- 読んだコミット：<SHA>（プルリクエストならベース <SHA> とヘッド <SHA>）
- 読んだ文書：<ファイルの一覧と行の範囲>
- 拠りどころにした文書：<見つけた文書。なかったもの>
- 適用した表記の規則：<規則の出どころ>
- 読み方：素読み／突き合わせ
- 視点：<割り当てた視点>
- 走らせたツール：<コマンドと終了コード、拾った件数>
- 走らせなかったツールと理由：<未導入など>
- 指摘の件数：高 N、中 N、低 N、確認事項 N
- 読み残した範囲：<あれば>
```

### 一件の形

```markdown
### [高] C-001 主張：`tool lint` が警告で非ゼロ終了すると書いている

- 位置：manual/chapters/07-check.md:58
- 引用：「警告が一つでもあれば、tool lint は失敗します。」
- 問題：仕様書は、警告だけなら正常終了すると定めている。読み手は CI の設定を誤る。
- 根拠：docs/specifications.md:1624「`tool lint` はエラーが一つでもあれば非ゼロで終了し、警告だけなら正常終了する。」
- 修正案：「tool lint は、エラーが一つでもあれば失敗します。警告だけなら成功として終わります。」
- 段と視点：段 3、初めての利用者
```

上の例は書き方を示すためのもので、実際の箇所ではない。

- 番号の頭の文字は種類を表す（S 構造、T 用語、C 主張、X 文書間、L 言葉、Q 確認事項）。
- 引用は原文のまま、一文か一行にとどめる。
- 根拠には file:line と、その行の引用か要約を書く。
  コードを根拠にするときは、関数か定義の名前も書く。
- 修正案は、リポジトリの表記の規則に従って書く。
  修正案を一つに決められないときは、選択肢を並べて確認事項にする。
- 確認事項には、根拠を探した範囲（検索した語とディレクトリ）を書く。

### 末尾

- 同じ原因から出た指摘のまとまり（たとえば「ADR NNNN の変更が仕様書の三箇所に反映されていない」）
- ツールの規則や、このスキルの表に足すとよい規則
