# 精読モードの下調べ

精読モード（`close-reading` スキル）の手順を決めるために調べた文献とツールを、要約してまとめる。
調べた日は 2026-10-17 である。
ライセンスと版は、npm のレジストリと GitHub の API で確かめた値を書く。
確かめられなかった事柄は「未確認」と書く。

## 1. 出版の校正と校閲

### 校正と校閲の区別

校正は、原稿とゲラ（校正刷り）を照らし合わせて、文字と形の誤りを正す作業である。
校閲は、校正に加えて、内容の矛盾や事実の誤りを調べて確かめる作業である。
講談社の校閲部は、この区別をそのまま説明している（[講談社 校閲力養成セミナーの案内](https://gendai.media/articles/-/147322)、[同 「校閲者はどう迷うか」編](https://gendai.media/articles/-/164656)）。

精読モードへの写し方は次のとおりである。

- 校正にあたるのは、表記の規則（一文一行、ダッシュ、中黒、用語の使い分け）の検査である。機械的に拾えるものは、ツールと grep に任せる。
- 校閲にあたるのは、事実の確認（文書の主張とコードの突き合わせ）、論理の矛盾、文書間の食い違いである。ここは人（エージェント）が読む。

### 照合の技法

- **引き合わせ（突き合わせ）**：原稿とゲラを一字ずつ照らし合わせる。資料によっては、前の校で入れた赤字が次のゲラに反映されたかを確かめる作業（赤字合わせ）を突き合わせと呼ぶ。定義は資料によって揺れる（[アドタイの記事](https://www.advertimes.com/?p=480546)、[リアルサウンドの記事](https://realsound.jp/book/2022/09/post-1127283.html/amp)）。
- **素読み**：元の原稿と照らさずに、ゲラだけを読んで違和感を拾う。校閲に寄った読み方である。
- **事実確認**：固有名詞、数、日付、引用を、一次資料で確かめる。講談社の校閲部はセミナーで、事実確認の目的とこつを一つの単元にしている（[講談社の記事](https://gendai.media/articles/-/147322)）。

精読モードでは、プルリクエストの差分を読むときを突き合わせ（前の版と、直すべき箇所の反映を確かめる）、文書を丸ごと読むときを素読みとして扱う。
事実確認の一次資料は、コードとテストである。

### 表記の基準

- **JTF 日本語標準スタイルガイド（翻訳用）**：日本翻訳連盟が出す、翻訳のための表記の基準。最新は 4.0（2026-07-25）で、3.0 から CC BY 4.0 で公開している（[JTF のページ](https://www.jtf.jp/tips/styleguide)）。全角と半角のあいだに空白を入れない規則があり、空白を入れる表記のリポジトリとは合わない。丸ごとは採らず、句読点や括弧の考え方を参考にとどめる。
- **公用文作成の考え方**（文化審議会の建議、2022-01-07）：昭和 26 年の「公用文作成の要領」に代わる手引き。一般に向けた文書は義務教育で学ぶ範囲の知識で読めるように書く、という考え方が、使い手のマニュアルの「説明していない語をいきなり使わない」と同じ向きにある（[文化庁の報道発表](https://www.bunka.go.jp/koho_hodo_oshirase/hodohappyo/93650001.html)）。
- **記者ハンドブック**（共同通信社）：新聞の用字用語の基準。市販の書籍であり、辞書としてツールに取り込める形の公開はない。精読モードでは参照先として名前を挙げるにとどめる。

## 2. 技術文書のレビューの方法

### Fagan インスペクション

Fagan が IBM で定式化した、役割（モデレーター、作者、読み手、テスター）と段階（計画、概観、準備、会議、手直し、追跡）を持つ形式的なレビューである。
欠陥の記録を残し、その統計で工程を直していく点が要である（M. E. Fagan, "Design and code inspections to reduce errors in program development," IBM Systems Journal 15(3), 1976, pp. 182-211、[IEEE Xplore](https://ieeexplore.ieee.org/document/5388086)、[論文の PDF](https://www.ida.liu.se/~TDDC90/labs/lab-papers/fagan76.pdf)）。

精読モードに取り入れるのは、次の二点である。

- 段を分けること（読む人が各自で準備し、まとめ役が統合する）。サブエージェントを読み手、親のエージェントをモデレーターに当てる。
- 指摘を同じ形で記録すること（位置、種類、重大度）。

### チェックリストによる読み、シナリオによる読み

チェックリストは、何を探すかを問いの一覧で与える。
シナリオによる読み（scenario-based reading）は、欠陥の種類ごとに読み手へ別々の手順を与える。
Porter、Votta、Basili の実験では、シナリオの読み手がその場任せの読みとチェックリストの読みより約 35% 多く欠陥を見つけ、チェックリストはその場任せと差がなかった（A. A. Porter, L. G. Votta, V. R. Basili, "Comparing detection methods for software requirements inspections: a replicated experiment," IEEE TSE 21(6), 1995, pp. 563-575、[UMIACS の書誌](https://sites.umiacs.umd.edu/node/16314)）。
ただし、Fusaro らの独立した追試では、シナリオの優位は再現しなかった（[Stickyminds の解説](https://www.stickyminds.com/article/comparing-detection-methods-software-requirements-inspections)）。
効果の大きさは確かでないが、「読み手ごとに探すものを分け、手順で与える」形は、サブエージェントへの指示の書き方としてそのまま使える。

### 視点による読み（PBR）

Perspective-Based Reading は、読み手ごとに文書の使い手の役（利用者、設計者、テスター）を割り当て、その役が文書から作るもの（利用の手順、設計、テストの計画）を実際に作りながら読ませる方法である。
役を組み合わせると、同じ人数がいつもの読み方をするより、文書の広い範囲から欠陥が見つかる、というのが中心の主張である（V. R. Basili ほか, "The Empirical Investigation of Perspective-Based Reading," Empirical Software Engineering 1(2), 1996, pp. 133-164、[UMD の技術報告 CS-TR-3585](https://www.cs.umd.edu/users/basili/publications/technical/T136.pdf)、[DRUM](https://drum.lib.umd.edu/items/7eb0ef0c-4045-4a28-b7ca-b8e2df410d16/full)）。
要求の検査への応用の解説は F. Shull, I. Rus, V. Basili, "How Perspective-Based Reading Can Improve Requirements Inspections," IEEE Computer 33(9), 2000, pp. 73-79 にある。
Ciolkowski らの追試（1997）は、その場任せの読みに比べて個人とチームの検出率が上がることをおおむね確かめた。

精読モードでは、使い手のマニュアルの読み手（編集者、DTP オペレーター、著者）と、開発者のマニュアルと仕様書の読み手（開発者、テストを書く人）を視点に当てる。
各視点には「その役としてこの文書から何を作るか」（入稿までの手順、テストのケース、プラグインの最小の実装）を課す。

### 要求の品質の特性と曖昧さ

- **ISO/IEC/IEEE 29148:2018** は、個々の要求の特性（曖昧でない、単一である、検証できる、など）と、要求の集合の特性（完全、一貫している、など）を分けて定める。規格の本文は有料なので、二次資料で確かめた（[規格のプレビュー（2011 年版）](https://webstore.ansi.org/preview-pages/ISO/preview_ISO+IEC+IEEE+29148-2011.pdf)、[Requirements Smells の論文](https://arxiv.org/pdf/1611.08847)）。精読モードでは「この文からテストを書けるか」（検証できるか）を、仕様書と ADR の読みの問いにする。
- **Ambiguity Handbook**（D. M. Berry, E. Kamsties, M. M. Krieger, "From Contract Drafting to Software Specification: Linguistic Sources of Ambiguity," 2003）は、一見曖昧でない語（すべて、各、only、also、and と or の結合の強さ、代名詞の指す先、修飾の係り先）が生む曖昧さを集めた手引きである（[PDF](https://cs.uwaterloo.ca/~dberry/handbook/ambiguityHandbook.pdf)）。日本語では「すべて」「各」「のみ」「など」「かつ／または」「以上／超える」「場合／とき」「それ／これ」と、連体修飾の係り先に置き換えて、言語の段の問いにする。

### 人文学の精読

文学研究の close reading（語の選び方、反復、文の構造に注意を払って読む）は、技術文書の欠陥を探す目的とは合わないので、取り入れない。
語の反復と揺れに目を向ける点だけは、用語の段と重なる。

このほか、リポジトリの中のスクリプトと、リポジトリが作るツール自身が検査に使えることがある。

- 文書が参照する `docs/` の文書がビルドの読む一覧にあるかを検査するスクリプト（あれば）。
- 仕様書を変えたブランチがマニュアルも変えているかを検査するスクリプト（あれば）。
- 文書全体をエラーと警告なしで組めるかを確かめるビルドのスクリプト（あれば）。
- マニュアルの原稿の構文、評価、参照されないラベルを検査するコマンド（あれば）。
  表記の検査をこのコマンドが担うかは、リポジトリの仕様書で確かめる。
- 原稿をプレーンテキストに書き出すコマンド（あれば）。独自記法を除いた文を textlint に渡せる。

見出しの検査のスクリプトなど、役目を終えた可能性のあるものは、リポジトリの現在の既定のブランチにあるかを確かめてから使う。

## 4. 精読モードへの反映のまとめ

- 段を分けて読む（Fagan、シナリオによる読み）。
- 読み手の役を割り当て、役ごとに作るものを課す（PBR）。
- 校正にあたる表記の検査はツールと grep に任せ、エージェントは校閲（事実、論理、文書間）に時間を使う。
- 事実確認の一次資料はコードとテストとし、指摘には必ず file:line の根拠を付ける。
- 曖昧さの問いは Ambiguity Handbook の語の類を日本語に置き換えて使う。
- 仕様書と ADR は「この文からテストを書けるか」で読む（ISO/IEC/IEEE 29148 の検証できる要求）。
