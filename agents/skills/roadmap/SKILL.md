# ロードマップ (docs/roadmap.md)

ロードマップは、リポジトリにまだ無いものを書く文書である。
今の振る舞いは仕様書 (`docs/specifications.md`) に書き、ロードマップには書かない。
このスキルの決まりは、Golem (`tett23/golem`) の `docs/roadmap.md` を手本にしている (dotfiles の docs/adr/0125)。

## 置き場所

置き場所は `docs/roadmap.md` である。
モノレポでモジュールごとに持つときは、`docs/<module name>/roadmap.md` に置く。

## 冒頭の段落

冒頭の段落には、次のことを書く。

- 仕様書との分担。今の振る舞いは仕様書に書き、ロードマップには、まだ無いものだけを書く。版ごとの節 (または「扱う事項」の節) に載る項目は、どれもまだ無い。
- 載せる節の種類。版ごとの節のほかに、「手で確かめる項目」「未決事項」「課題にしなかった事項」もまとめる。
- ADR との関係。どの項目も、着手するときに ADR を作る。
- 項目を消すとき。実装を終えたら項目を消し、振る舞いを仕様書に書く。

## 節

節は、次の順に置く。

1. 「リリースの予定」: 次に出す版と、その後の予定を書く。
今の時点の計画であり、変わりうると書く。
版の付け方は、仕様書の該当の節へのリンクで引く。
2. 版ごとの節と、先に回した事項の節 (「v2 以降に回した事項」など)。
   - 版の節は、主題ごとの小見出しに分けてよい。
   - 時期を決めていない版の節 (「v3 より前（時期は未定）」など) を置いてよい。
   - 版の無いリポジトリでは、版ごとの節の代わりに「扱う事項」の一つの節にしてよい。
   - 扱う項目をすべて実装した版の節は、「<版> で扱う項目は、すべて実装した。」の一文だけを残す。
3. 「手で確かめる項目」: 実装と自動のテストは終わったが、ADR が求める手作業の確かめが残っている項目。
4. 「未決事項」: 決まっていない事項。
5. 「課題にしなかった事項」: 扱わないと決めた事項。
扱う必要が出たら、新しい ADR で決め直す。

「手で確かめる項目」「未決事項」「課題にしなかった事項」は、項目が無いときは節を置かない。

## 項目の形

項目は、次の形の箇条書きで書く。

- **<名前>**：<説明>

説明には、理由、ほかの項目との順序、関係する ADR へのリンクを書く。
説明の下に、入れ子の箇条書きを使ってよい。
確かめる時期や対象の版があるときは、名前の後に「（v1.0.0 のリリースで確かめる）」のように添える。
未決事項のうち、次に出す版より後の版のための事項には、その版を添える。

## ADR との関係

- どの項目も、着手するときに ADR を作る。
- `accepted-pending` の ADR がある項目には「（未実装）」と書き、その ADR へリンクする。
- `superseded-pending` の ADR がある項目にも「（未実装）」と書き、元の ADR と修正先の ADR へリンクする。修正先の無い注記 (`kind` が `note`) だけのときは、元の ADR へリンクする。

## 並べ方

項目は、上から順に実装できるように並べる。
ほかの項目に依る項目は、その項目の後に置く。

## 項目を消すとき

項目は、実装を終えるまで残す。

- 実装を終えたら、同じ変更で、その項目を消し、振る舞いを仕様書に書く。
- 手で確かめる項目は、確かめた結果を実装のプルリクエストか `docs/audits/` の記録に書いた後に消す。
- 未決事項は、決めたことを仕様書か ADR に書いた後に消す。

ロードマップから消した項目は、仕様書、ADR、Git の履歴で追う。
