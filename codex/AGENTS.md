## 原則

Codexの出力は日本語で書く。
コミットログは英語で書いて、リリースノートも英語で書く。CHANGELOGも英語で書く。
技術用語のカタカナ語や英語は、分野で慣用されている形のまま使い、漢語に置き換えない（シード値、トークン、キャラクターアークなど）。

## ADR（docs/adr/）

実装に入るまえに必ずADRを作成する。一度コミットしたADRはステータスの行を除き、変更不可。作成時点ではコミットをせず、人間のレビューを受ける必要がある。
仕様を変更したくなった場合は、新たに修正用のADRを作成する。元のADRを書きかえてはいけない。
ADRを破棄する場合は、ステータスを破棄にして、理由をdocs/specifications.mdに記述する。

変更を不可にする方法は以下にある。リポジトリを初期化するときにはREADMEに従うこと。
https://github.com/tett23/adr-guard

具体的には、次の 3 つを行う。Codex の hook は全体の設定 (`~/.codex/hooks.json`) で有効なので不要。

1. `.githooks/pre-commit` を置き、実行権限を付ける。ほかの検査と並べる場合は、`exec` の行を最後に置く。

   ```sh
   #!/bin/sh
   exec adr-guard pre-commit --allow-status --allow-links
   ```

2. clone ごとに `git config core.hooksPath .githooks` を実行する (README にも手順を書く)。
3. CI に adr-guard の `adr` ジョブを足す (adr-guard の README の例のとおり)。

### ADRの構成

docs/adr/ に配置する。ファイル名には `0001-feature-details.md` のように連番のprefixをつけなくてはいけない。連番以降はkebab-caseで、内容を表すような人間に可読な名前をつける。

### ADRの中身

ADRは以下のような内容を記載する。ステータスはこのADRがどのような状態にあるかを示す。データ構造やアルゴリズムを変更する場合は、その節も立てる。仕様の調査に使った文献はADRの末尾に含めること。そのほか、仕様検討時のログとして残したほうがよいことがあれば節を立てる。

```
# ADR 0001: タイトル

ステータス: {採択／採択（未実装）／採択→変更後ADR番号／採択→○○（変更部分）はADR NNNN／提案／却下／破棄など}

## 文脈

## 実装すること

## 実装しないこと

## 不変条件

## テスト設計

## トレードオフ

## 参考文献

（ない場合はなしと記載）
```

振る舞いを決める ADR は、「不変条件」の節を持つ。どの入力でも成り立つ性質を、テストの述語として書ける形で一つずつ番号を付けて書き、境界の入力（空、一つ、ちょうど収まる、一つあふれる、など）の表を添える。テストの名前には、その番号を入れる。不変条件を書けない ADR（設定の値や手順だけを決めるもの）は、その節に「なし」と理由を書く。

ADR作成後とドキュメント更新後は `adr-guard links --fix` でADRのリンクをチェックし、修正する。

ADR を書いた後は、本人のレビューに出す前に、`close-reading` スキルで ADR を精読し、指摘を直す。

### チャットでのADR表記

モノレポやマルチモジュールのリポジトリでは、チャット、コミットログ、PRでADR番号を示すときは番号だけでなく、`<module name> ADR NNNN` のように明示する。

### 未実装ADRの自動実装

採択（未実装）ADR を実装するよう頼まれたときの、デフォルトの指示は以下。

```
ADRを全て読み、ステータスが採択（未実装）で現状実装可能なものを全て実装。実装が止まりそうなときはその場所を後回しにしてもよい。実装はADRごとにpull-reqを作成する。CIが通ればpull-reqはマージコミットでマージしてよい。停止後、どこを後回しにしたかのレポートをチャットに出力すること。実装のpull-reqには実装が終わったものはステータスを採択にする変更を含める。
```

## docs/specifications.mdとREADME.md

ADRにより仕様が変更されたら、仕様とREADMEも同時に編集する。このふたつのドキュメントはmain/masterにおいて常に最新でなくてはならない。

その他、監査、性能計測のスナップショット、バージョンごとの性能を表したグラフもdocs/以下に適切なディレクトリを切って配置する。これらもコミット後は変更不可。

specifications.mdからADRを示すときは、リンクつきでなければならない。

## 文書の書き方

README、仕様書、ADR、マニュアルなど日本語と英語の文書は、パラグラフライティングで書く。

読み手は文書ごとに次のとおりとし、その読み手が知らないことを前提にせずに書く。

- 仕様書と ADR: 本人、コントリビューター、会話の文脈を持たずに文書だけを読む AI。
- README: そのリポジトリについて何も知らない人。
- マニュアル: そのソフトウェアやプロダクトに初めて触れる人。

書き方は次のとおり。

- 一つの段落には一つのトピックだけを置く。いくつものトピックや手順が混ざった長い段落は分ける。
- 段落の最初の文でその段落のトピックを示す。最初の文だけを拾い読みしても、論の流れを追えるようにする。
- 前の段落との論理の関係を、段落の頭の接続の言葉で示す（しかし、そのため、実際、であれば など。英語では However、Therefore など）。
- 一文には一つの事柄だけを書く。主語と述語を対応させ、「これ」「その」が何を指すかを明らかにする。
- 関係する内容は一つの節にまとめ、用語は使う前に定義する。定義した用語は、文書の中で別の語に言い換えない。
- 列挙の性質のものは箇条書きか表にする。ただし、短い列挙は文の中に書いてよい。脇道の補足は本文ではなく脚注に下ろす。
- 論は一方向に進める。主張を置き、反論を処理し、結論は一度だけ置く。
- 確かめた事実と、推測や意見を分けて書く。確かめていないことは「未確認」と書く。
- 意味を足さない言い回し（「〜することができる」「重要なのは」「〜と言えるでしょう」など）を使わない。
- 仕様書・README・マニュアルを組み直すときは、振る舞いを変えず、落とさず、弱めず、足さない。数値、診断のコード、キー、既定値、ADR へのリンク、アンカーがすべて残ることを、書き直す前と後の一覧で確かめる。コミットした ADR は組み直さない（ADR の節を参照）。
- 書いた後に、各段落の最初の文だけを読み通し、論の流れが追えるかを確かめる。

## Git運用方針

main/masterに対するrebaseは原則禁止。APIキーが漏れたときなどは例外とする。
ブランチに対してはマージするまではrebaseを許可する。マージは常にno-ffで行う。

### タグとリリース

`v` から始まるタグはリリース対象とする。 `v0.0.1-rc` のようなタグはpre releaseとして扱う。

リリースノートには、変更点を「追加」「変更」「削除」「修正」などの項目に分けて書く。必要ならほかの項目も足す。可能であれば、各変更を行ったコミット（または PR）とADRを添える。ADRのリンクは絶対リンクとする。
リリースノートはGitHubのReleasesに書く。

## ツール

### sed, awk, make

AIがローカルで使う場合はGNU版を使う。zshrcでGNU版を使うようにしているので、特別な操作をする必要はない。
dotfiles のスクリプトは自分の手元でだけ動くので、コミットするものでも GNU 版を優先する。ただし、install.sh と bootstrap.sh は Nix と mise のセットアップの前に実行されるので、BSD 版を前提とする。
ほかのリポジトリのスクリプトは、動かす環境にあるもの (macOS なら BSD 版) でも動くように書く。

### find, grep

fd, rgが入っているのでローカルの調査ではこちらを優先する。
コミットするスクリプトではfindとgrepを優先する。

### ai-chat-log

ai-chat-logsリポジトリ (https://github.com/tett23/ai-chat-logs) で過去のチャットログを全て保存している。
`chat-log` コマンドで過去のコンテキストを復元できるので、必要であればコンテキストを復元する。
まず `chat-log context` でいまのプロジェクトの最近のセッションを知り、`chat-log search <語> --cwd .` で決定や議論を探し、
`chat-log show <ID> --around <番号>` で前後の会話を読む。詳しくは `chat-log --help`。

## 実装方針

UNIX哲学にもとづき、GUIや重量級アプリケーションを除けば、小さなツール群でプロダクトを構築する。
また、常にeasy (手近で慣れたもの) よりsimple (要素が絡み合わないもの) な設計と実装を選択する。
参考: Rich Hickey「Simple Made Easy」(Strange Loop 2011) https://www.infoq.com/presentations/Simple-Made-Easy/

ADR のテスト設計に書いたテストを先に書いて失敗させてから実装する。自動テストを書けない変更（設定の値など）は、ADR のテスト設計に確かめ方を書き、実装の後に実際に動かして確かめる。

ライセンスに問題がなく、再実装が容易であればdependenciesに入れるのではなく、再実装する。その際、テストは本家を参考にしつつ十分に厚く書くこと。必要な機能が限られている場合は、必要な機能だけを実装してよい。

### Rust

関数型プログラミングのスタイルを優先すること。

### TypeScript

クラス使用禁止。

### Python

自分が使わないので、スクリプト等をコミットしないようにする。可能な限りシェルスクリプトで実装する。できない場合は相談して。
AIが作業用に使うのは問題ありません。
ファイルに Python を書き出さない。ツールとして使うのはよい。

## モデルの使い分け

既定のモデルは `gpt-6-astra` とする (Claude の Opus に当たる)。ADR、設計の判断、本人への報告は既定のモデルで行う。
次の作業は、モデルを固定したサブエージェントの役割 (`~/.codex/agents/` の `auditor`・`reader`・`runner`) に任せる (docs/adr/0117)。

### `auditor` に任せる (`gpt-6-astra`、推論 `xhigh`。Claude の Fable に当たる)

深い読みと厳密さが要る作業。

- ADR と実装、テストの乖離の調査。ADR の「実装すること」「実装しないこと」「テスト設計」が実装とテストに表れているかを確かめ、乖離を `file:line` と ADR の該当箇所つきで返す。
- セキュリティ監査。
- そのほか、本人が `auditor` を使うよう明示して頼んだとき。

### `reader` に任せる (`gpt-6-sol`。Claude の Sonnet に当たる)

読んで理解する必要はあるが、判断の基準が決まっている作業。

- 外部のリポジトリ (ghq で取得したもの) のソースを読み、問いへの答えを、根拠の `file:line` と短い引用つきで返す。
- 長いログやドキュメントを読み、要る所を抜き出す。
- 確かめのためのスクラッチのスクリプトを書いて動かし、結果を返す。
- 採択された ADR とテストがそろっている、機械的な実装 (名前の置き換え、決まった形の設定を足すなど)。

### `runner` に任せる (`gpt-6-luna`。Claude の Haiku に当たる)

決まった手順を動かし、結果を数えて返す作業。

- テストや lint を動かし、通った数と、失敗したテストの名前とメッセージだけを返す。
- 確かめのスクリプトを多くの入力に対して動かし、数を返す (例: 例のファイル全体をインデントし直して、変わった行を数える)。
- 定義や使われている所を `rg` で探し、`file:line` の一覧を返す。
- `nix search` や `mise registry` で名前を調べる。
- `gh` で CI の結果を見て、失敗したジョブとログの該当部分だけを返す。

### 任せるときの決まり

- 返す形を指定する: 動かしたコマンド、数値、`file:line`。ADR に書く事実は、この形で返ったものだけを使う。
- サブエージェントが「確かめた」と言っただけのことは、ADR やコミットに書かない。根拠のコマンドと出力が返ったものだけを書く。
- 数行のコマンドで済む確かめは、任せずにメインで行う。
- 仕様に関わらない簡易な調べものは `reader` に任せる。裏取りが要るときは、難しさに応じて既定のモデルか `auditor` で行う。
- 調べものは、別のサブエージェントに分けてよい。
- 過去の文脈、調査、実装の内容が要るときは、`chat-log` コマンドで取得する。
- `auditor` の調査や監査の結果は、要約し直さずに、指摘をそのまま本人に示す。

## 外部のリポジトリを調査するとき

外部のリポジトリの調査をするとき、ネットワークアクセスを毎回やるのは時間の無駄である。調査のためのリクエストを繰りかえすときは `ghq` でリポジトリを取得すること。GitHub上のリポジトリであれば無許可で取得してよい。

### 外部のリポジトリにissueやpull-reqを送るとき

実機で調査していないことを文章にしないこと。必ず動作を確認したことだけを書く。動作確認していないissueを立てるのはAI slopで、upstreamのメンテナを疲弊させるので、絶対にしてはいけない。
