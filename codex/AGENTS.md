## 原則

Codexの出力は日本語で書く。
コミットログは英語で書いて、リリースノートも英語で書く。CHANGELOGも英語で書く。
技術用語のカタカナ語や英語は、分野で慣用されている形のまま使い、漢語に置き換えない（シード値、トークン、キャラクターアークなど）。

## スキル

全リポジトリで使うスキルと、使うときと使いかたは次のとおりである。使うときが来たら、作業の前にそのスキルを読み、その手順に従う。

| スキル | 使うとき | 使いかた |
| --- | --- | --- |
| `adr` | ADR を書く、直す、採択する、実装する、破棄する前。リポジトリに adr-guard を入れる前。未実装の ADR をまとめて実装する前 | テンプレート、状態の遷移、採択の記録のしかたに従う。ADR は既定のモデルで書く |
| `doc-writing` | README、仕様書、ADR、マニュアルなどの文書を書く前、直す前 | パラグラフライティングと、文書ごとの読み手の決まりに従って書く |
| `close-reading` | 文書を変えた後、本人に出す前。ADR を採択する前。文書を変えるプルリクエストをレビューするとき。精読やレビューを頼まれたとき | 読む範囲 (全文か差分か) をスキルの決まりで決める。精読はサブエージェントに任せてよい。指摘は、根拠を確かめてから直す |
| `release` | タグを打つ前。リリースノートや CHANGELOG を書く前 | タグの名前と、リリースノートの項目の分け方とリンクの決まりに従う |
| `context-restore` | セッションの始め。過去の決定、調査、実装の経緯を聞かれたとき。前のセッションの続きを頼まれたとき | `chat-log` を `context`、`search`、`show --around` の順に引き、根拠の `<ID>#<番号>` を添えて返す |
| `roadmap` | ロードマップを書く前、直す前。項目の実装を終えた後、手で確かめた後、未決事項を決めた後で、その項目をロードマップから消す前 | 節と項目の形に従い、実装を終えた項目は消して仕様書に書く |
| `security-audit` | セキュリティの監査を頼まれたとき。本人が「監査」とだけ頼んだとき | `auditor` に任せ、指摘を変えずに記録するか返す |
| `conformance-audit` | ADR 違反と予算違反の監査を頼まれたとき。本人が「監査」とだけ頼んだとき。予算を決める前、変える前 | `auditor` に任せ、指摘を変えずに記録するか返す。予算は ADR と予算の一覧の両方に書く |

スキルを足したり、使うときや使いかたを変えたりしたときは、この表も同じく変える (docs/adr/0127)。

## ADR（docs/adr/）

実装に入るまえに必ずADRを作成する。一度コミットしたADRはステータスの行を除き、変更不可。作成時点では `Status: proposed` で書き、人間のレビューを受けるまでコミットしない。

### チャットでのADR表記

モノレポやマルチモジュールのリポジトリでは、チャット、コミットログ、PRでADR番号を示すときは番号だけでなく、`<module name> ADR NNNN` のように明示する。
ルートの `docs/adr/` の ADR は `root ADR NNNN` と、リポジトリの外の ADR は `<リポジトリ> ADR NNNN` と書く (docs/adr/0124)。

## docs/ の構成

`docs/` の標準の構成は次のとおりである (docs/adr/0129)。

| パス | 中身 | 変えてよいか | 置くか |
| --- | --- | --- | --- |
| `docs/adr/` | ADR | コミットした後はステータスの行とリンクのほかを変えない | 必ず置く |
| `docs/specifications.md` | 仕様。今の振る舞いを書く。ADR と食い違うときは ADR が正。ADR から作り直せるように書く | 変えてよい | 仕様があれば置く |
| `docs/roadmap.md` | ロードマップ。まだ無いものを書く | 変えてよい | あれば置く |
| `docs/budgets.md` | 予算の一覧。ADR と食い違うときは ADR が正 | 変えてよい (ADR と同じ変更で) | 予算があれば置く |
| `docs/glossary.md` | 用語集 | 変えてよい | あれば置く |
| `docs/research/` | 調査のまとめ | 変えてよい | あれば置く |
| `docs/audits/` | 監査の記録 | コミットした後は変えない、消さない、移さない | 記録があれば置く |
| `docs/benchmarks/` | ベンチマークの記録 | コミットした後は変えない、消さない、移さない | 記録があれば置く |

- 表のほかのファイルやディレクトリを `docs/` に置いてもよい。表と同じ中身のものは、表のパスに置く。
- モノレポでは、`docs/<module name>/` に、表と同じ構成を置ける。`docs/<module name>/adr/` は必ず置き、ほかは置かなくてもよい。リポジトリのルートの `docs/` には、モジュールに属さないものを置く。
- 記録の変更不可の決まりは、標準の `docs/audits/` と `docs/benchmarks/` に加えて、adr-guard が記録として扱う単数形の `docs/audit/` と `docs/benchmark/` にも当てはめる。新しい記録は、標準の複数形のディレクトリに書く。訂正や追加の調査と計測は、新しいファイルに記録する。
- 表のパス (モノレポの `docs/<module name>/` の下のものを含む) の中だけの変更では、CI のビルドとテストを省く。ただし、ビルドやテストの入力になるファイルの変更では省かない。`docs/budgets.md` の変更では、予算の確かめ (`bin/budget-check`) を省かない。予算の確かめを CI のどのイベントで動かすかは、各リポジトリの ADR で決める。文書の検査と、ADR と記録の変更不可の検査は省かない。

ADRにより仕様が変更されたら、仕様とREADMEも同時に編集する。このふたつのドキュメントはmain/masterにおいて常に最新でなくてはならない。

監査とベンチマークの記録 (性能の計測のスナップショット、バージョンごとの性能を表したグラフを含む) は、表の `docs/audits/` と `docs/benchmarks/` に置く。

specifications.mdからADRを示すときは、リンクつきでなければならない。

## 文書の書き方

文書は、パラグラフライティングで書く。
文書を変えたら、本人に出す前に `close-reading` スキルで精読し、指摘を直す。

## Git運用方針

main/masterに対するrebaseは原則禁止。APIキーが漏れたときなどは例外とする。
ブランチに対してはマージするまではrebaseを許可する。マージは常にno-ffで行う。

## ツール

### sed, awk, make

AIがローカルで使う場合はGNU版を使う。zshrcでGNU版を使うようにしているので、特別な操作をする必要はない。
dotfiles のスクリプトは自分の手元でだけ動くので、コミットするものでも GNU 版を優先する。ただし、install.sh と bootstrap.sh は Nix と mise のセットアップの前に実行されるので、BSD 版を前提とする。
ほかのリポジトリのスクリプトは、動かす環境にあるもの (macOS なら BSD 版) でも動くように書く。

### find, grep

fd, rgが入っているのでローカルの調査ではこちらを優先する。
コミットするスクリプトではfindとgrepを優先する。

### ai-chat-log

過去の Claude Code と Codex の会話は、ai-chat-logs リポジトリ (https://github.com/tett23/ai-chat-logs) にすべて保存してあり、`chat-log` コマンドで引ける。

## 実装方針

UNIX哲学にもとづき、GUIや重量級アプリケーションを除けば、小さなツール群でプロダクトを構築する。
また、常にeasy (手近で慣れたもの) よりsimple (要素が絡み合わないもの) な設計と実装を選択する。
参考: Rich Hickey「Simple Made Easy」(Strange Loop 2011) https://www.infoq.com/presentations/Simple-Made-Easy/

ADR のテスト設計に書いたテストを先に書いて失敗させてから実装する。自動テストを書けない変更（設定の値など）は、ADR のテスト設計に確かめ方を書き、実装の後に実際に動かして確かめる。

ライセンスに問題がなく、再実装が容易であればdependenciesに入れるのではなく、再実装する。その際、テストは本家を参考にしつつ十分に厚く書くこと。必要な機能が限られている場合は、必要な機能だけを実装してよい。

### Rust

関数型プログラミングのスタイルを優先すること。

### TypeScript

クラス使用禁止。

### Python

自分が使わないので、スクリプト等をコミットしないようにする。可能な限りシェルスクリプトで実装する。できない場合は相談して。
AIが作業用に使うのは問題ありません。
ファイルに Python を書き出さない。ツールとして使うのはよい。

## モデルの使い分け

既定のモデルは `gpt-6-astra` とする (Claude の Opus に当たる)。ADR、設計の判断、本人への報告は既定のモデルで行う。
どの作業をどの役割 (`~/.codex/agents/` の `auditor`・`reader`・`runner`) に任せるかは、各役割の説明 (`description`) に従う (docs/adr/0117)。

### 任せるときの決まり

- 返す形を指定する: 動かしたコマンド、数値、`file:line`。ADR に書く事実は、この形で返ったものだけを使う。
- サブエージェントが「確かめた」と言っただけのことは、ADR やコミットに書かない。根拠のコマンドと出力が返ったものだけを書く。
- 数行のコマンドで済む確かめは、任せずにメインで行う。
- 仕様に関わらない簡易な調べものは `reader` に任せる。裏取りが要るときは、難しさに応じて既定のモデルか `auditor` で行う。
- `reader` の調べが足りないとき (根拠が無い、問いに答えていない、食い違いがある) は、難しさに応じて既定のモデルか `auditor` で調べ直す。
- ADR はサブエージェントに書かせず、既定のモデルで書く。
- 調べものは、別のサブエージェントに分けてよい。
- 過去の文脈、調査、実装の内容が要るときは、`context-restore` スキルの手順で `chat-log` から取得する。
- `auditor` の調査や監査の結果は、要約し直さずに、指摘をそのまま本人に示す。

## GitHub actions

CI は、ドキュメント類だけの更新ではビルドとテストを省略する。`README` や `CONTRIBUTING` (`README.md`、`CONTRIBUTING.md` など) も対象に含む。ビルドやテストの入力になるファイル、コード、依存関係、設定、CI のワークフローに変更がある場合は省略しない。標準の構成の `docs/` のパスの中だけの変更は、「docs/ の構成」の決まりに従う。ほかの `docs/` のファイルは、ビルドやテストの入力になるかで判断する (docs/adr/0129)。

ドキュメント類だけの更新でも、文書の検査と、ADR・audit・benchmark の変更不可を確認する検査は省略しない。

Nodeは常に最新LTSを使用する。
GitHub actionsはNode 24以降で動く最新のメジャー版を使う。

## 外部のリポジトリを調査するとき

外部のリポジトリの調査をするとき、ネットワークアクセスを毎回やるのは時間の無駄である。調査のためのリクエストを繰りかえすときは `ghq` でリポジトリを取得すること。GitHub上のリポジトリであれば無許可で取得してよい。

### 外部のリポジトリにissueやpull-reqを送るとき

実機で調査していないことを文章にしないこと。必ず動作を確認したことだけを書く。動作確認していないissueを立てるのはAI slopで、upstreamのメンテナを疲弊させるので、絶対にしてはいけない。
